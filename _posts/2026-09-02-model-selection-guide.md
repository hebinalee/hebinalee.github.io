새 프로젝트를 시작할 때마다 같은 질문과 마주칩니다. 오픈소스 모델을 직접 서빙할지, 아니면 API를 그대로 쓸지. 지난 글들에서 서빙과 파인튜닝, Agent, RAG를 다뤘지만 정작 "어떤 모델을 쓸 것인가"는 다루지 않았어서, 이번엔 그 기준을 정리해봤습니다.

### 대부분의 경우, API가 정답이다

의외로 결론부터 말하면, 하루 처리량이 꾸준히 2~5백만 토큰을 넘지 않는다면 API를 쓰는 게 운영 비용과 속도 면에서 더 유리합니다. 자체 서빙이 더 저렴해지는 손익분기점은 대략 하루 1천만~3천만 토큰 구간부터로 알려져 있고, 이마저도 모델 크기와 인프라 구성에 따라 달라집니다. "직접 띄우면 무조건 싸다"는 생각과 달리, 실제로는 꽤 높은 트래픽이 지속돼야 역전이 일어납니다.

### 오픈소스를 선택해야 하는 이유는 비용이 아닐 때가 많다

그럼에도 오픈소스를 선택하는 이유는 비용 하나만이 아닙니다.

- **데이터가 외부로 나가면 안 되는 경우**: 사내망 안에서만 추론이 이뤄져야 하는 도메인(의료, 금융 등)
- **파인튜닝이 필수인 경우**: 지난 파인튜닝 글에서처럼 LoRA/QLoRA로 도메인에 맞게 조정해야 한다면, 애초에 가중치에 접근 가능한 모델이 필요합니다
- **지연시간을 직접 통제해야 하는 경우**: 커머셜 API는 평소엔 TTFT 150~300ms 수준이지만, 트래픽이 몰리면 p99 지연시간이 1~2초를 넘기도 합니다. 자체 서빙은 이 변동성을 직접 관리할 수 있습니다

반대로 이런 이유가 없다면, 굳이 인프라를 직접 운영할 이유는 크지 않습니다.

### 직접 운영하면 따라오는 비용: 사람

70B급 모델을 FP16으로 그대로 올리면 GPU 메모리가 약 140GB(A100 80GB 두 장) 필요하지만, GGUF Q4로 양자화하면 48GB GPU 한 장, 심지어 고급 개인용 GPU에서도 돌아갑니다(MMLU-Pro 기준 품질 저하는 1~3% 수준). 다만 여기서 끝이 아닙니다. 오케스트레이션, 모니터링, 장애 대응까지 포함하면 작은 팀 기준으로도 DevOps/MLOps 인력이 0.5~1.0 FTE 정도는 붙어야 한다는 게 일반적인 추산입니다. 모델 자체는 무료여도, 이걸 안정적으로 운영하는 인건비는 무료가 아닙니다.

### API를 쓴다면: 하나만 고르지 말고 라우팅하라

API를 쓰기로 했다면, 모든 요청을 플래그십 모델 하나로 처리하는 건 비효율적입니다. 2026년 현재의 주류 전략은 **작업 난이도에 맞는 가장 저렴한 모델로 라우팅**하는 것입니다. 이 방식만으로 플래그십 모델 단일 사용 대비 전체 API 비용을 50~65%까지 줄일 수 있다고 알려져 있습니다. 대략적인 가격대 감을 잡으면 이렇습니다(백만 토큰당, 입력/출력).

- Claude Opus 4.6: $5.00 / $25.00 — 최고 성능대
- Gemini 3.1 Pro: $2.00 / $12.00
- GPT-5.2: $1.75 / $14.00
- Claude Sonnet 4.6: 준수한 성능에 1M 컨텍스트까지, 가성비 기본값으로 자주 언급됨
- Gemini 3.5 Flash: $0.50 / $3.00 — 20만 토큰 이하 컨텍스트에서 비용에 민감하다면 유력한 선택지

간단한 분류/요약 작업은 저렴한 모델로, 복잡한 추론이나 코드 생성처럼 품질이 중요한 작업만 상위 모델로 보내는 라우팅 구조가 실무에서는 기본값에 가깝습니다.

### 오픈소스로 간다면: 이제는 벤치마크가 태스크별로 갈린다

오픈소스 쪽도 하나의 "최고" 모델이 있다기보다 태스크별로 강점이 나뉩니다. 종합 추론·코딩에서는 Qwen 3 235B-A22B가 오픈소스 리더보드 상위권이고, 수학 추론은 DeepSeek 계열이, 긴 컨텍스트 처리(최대 1천만 토큰)는 Llama 4 Scout가, 코딩 벤치마크(SWE-bench)에서는 GLM-5 계열이 강점을 보인다고 알려져 있습니다. "이 모델이 무조건 낫다"보다 내 워크로드의 성격(코딩인지, 추론인지, 긴 문서 처리인지)에 맞춰 고르는 게 맞는 접근입니다.

### 정리하면

모델 선택은 결국 세 가지 질문으로 좁혀집니다. 트래픽이 자체 서빙이 남는 수준인가, 데이터/커스터마이징 때문에 가중치 접근이 꼭 필요한가, 그리고 API를 쓴다면 작업마다 라우팅을 나눌 준비가 되어 있는가. "일단 제일 좋은 모델부터 쓰고 보자"는 접근은 이제 비용 면에서도, 오픈소스 생태계가 다양해진 지금 상황에서도 최선이 아니라는 걸 확인했습니다.
