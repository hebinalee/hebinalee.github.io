멀티 에이전트 파일럿의 40%가 프로덕션 배포 후 6개월 안에 실패한다는 통계를 보고, 오히려 관심이 갔습니다. 에이전트를 여러 개 붙이면 더 똑똑해질 거라는 기대와 달리, 실제로는 왜 이렇게 실패율이 높을까 궁금했습니다.

### 가장 널리 쓰이는 구조: 오케스트레이터-워커

멀티 에이전트 패턴 중 가장 표준적인 건 **오케스트레이터-워커(orchestrator-worker)** 구조입니다. 오케스트레이터 하나가 작업을 받아서 하위 작업으로 쪼개고, 각각을 전문화된 워커 에이전트에게 위임한 다음, 결과를 다시 모아서 정리합니다. 보통 오케스트레이터는 강력한 모델을, 워커는 작업에 맞는 더 저렴한 모델을 씁니다 — 지난 모델 선택 글에서 다룬 라우팅 전략이 에이전트 단위로 확장된 셈입니다.

이 중에서도 **supervisor 패턴**이 가장 먼저 시도해볼 만한 구조로 꼽힙니다. Claude Agent SDK, LangGraph, OpenAI Agents SDK, CrewAI 등 대부분의 프레임워크가 기본으로 지원하고, 실패했을 때 무엇이 문제인지도 가장 잘 알려져 있어서 디버깅 참고 자료가 많습니다. 가장 단순한 패턴부터 시작하고, 필요할 때만 복잡한 구조로 넘어가라는 원칙은 여기서도 그대로 적용됩니다.

### 왜 40%가 실패하는가: 조율 비용은 생각보다 크다

에이전트가 하나에서 여러 개로 늘어나면, 그 사이의 통신과 조율 자체가 비용이 됩니다. 구체적으로 이렇습니다.

- **토큰 사용량**: 같은 작업이라도 멀티 에이전트 구조는 단일 에이전트 대비 3~10배 많은 토큰을 씁니다. 컨텍스트를 에이전트마다 중복해서 들고 있고, 조율 메시지가 오가고, 결과를 인계할 때마다 요약이 필요하기 때문입니다.
- **순차 작업에서의 성능 저하**: Google 연구에 따르면, 순차적으로 진행해야 하는 추론 작업에서 멀티 에이전트 조율이 단일 에이전트 대비 오히려 39~70% 성능이 떨어졌습니다. 정말 병렬로 나눌 수 있는 작업이 아니라면, 에이전트를 나누는 것 자체가 손해일 수 있습니다.
- **컨텍스트 윈도우 오버플로우**: 오케스트레이터는 모든 워커의 결과를 다 받아서 들고 있어야 하는데, 워커가 4개를 넘어가는 시점부터 컨텍스트 윈도우 한계에 부딪히는 경우가 흔합니다.
- **단일 장애점**: 오케스트레이터가 작업을 잘못 분류하면, 엉뚱한 워커에게 일이 넘어가고 이 오류는 뒤로 갈수록 잡기 어려워집니다.

### 그래서 언제 멀티 에이전트를 써야 하나

정리하면 멀티 에이전트가 유리한 상황은 명확합니다. **작업이 진짜로 병렬화 가능하거나, 역할이 진짜로 여러 개로 나뉘거나, 하나의 컨텍스트 윈도우에 다 담기엔 작업이 너무 큰 경우**입니다. 반대로 작업이 순차적이고, 컨텍스트가 크지 않고, 지연시간이 중요하다면 단일 에이전트로 충분하고 오히려 더 낫습니다. "에이전트를 여러 개 쓰면 더 똑똑해 보인다"는 인상과 실제 이득은 다른 문제입니다.

### 코드로 보면: 최소한의 오케스트레이터-워커

```python
workers = {
    "research": research_agent,   # 검색/조사 전담
    "coding": coding_agent,       # 코드 작성 전담
}

def orchestrate(task):
    # 오케스트레이터: 작업을 하위 작업으로 분해
    subtasks = orchestrator.plan(task)  # [{"worker": "research", "input": "..."}, ...]

    results = []
    for subtask in subtasks:
        worker = workers[subtask["worker"]]
        results.append(worker.run(subtask["input"]))

    # 오케스트레이터: 결과를 취합해서 최종 답변 생성
    return orchestrator.synthesize(task, results)
```

실제로는 여기에 워커별 실패 처리, 부분 실패 시 재시도, 컨텍스트 요약 로직이 더 붙지만, 뼈대는 "분해 → 위임 → 취합"이라는 세 단계로 요약됩니다. 이 뼈대 자체는 단순하지만, 워커 수가 늘어날수록 앞서 말한 조율 비용이 같이 늘어난다는 걸 감안해야 합니다.

### 정리하면

지금까지 시리즈에서 반복해서 나온 이야기이지만, 여기서도 결론은 같았습니다. 복잡한 구조가 항상 더 나은 답은 아니라는 것. 멀티 에이전트는 코디네이션 자체가 비용이라는 걸 전제로, 정말 병렬화가 필요하거나 역할 분리가 명확한 경우에만 쓰는 게 맞다는 걸 이번에 확인했습니다. 단일 Agent로 시작해서, 컨텍스트가 터지거나 병목이 명확해질 때만 나누는 게 여전히 가장 안전한 순서입니다.
